# 判斷力外化（Judgment Rubrics v1.0）

governance_parent: E:\AgentOS\AGENTS.md
目的：把需要判斷力的決策壓成 Sonnet 等級可機械執行的 rubric。每條附正例＋反例。
誠實聲明：rubric 補得了執行品質，補不了品味與模糊題。遇到 §6 列的情況，照 §6 處理，不要硬撐。

---

## 1. 何時該升級模型

**升級，若滿足任一：**
- 同一任務用相同規格失敗 ≥2 次，且失敗原因可排除「規格不清」（規格已含三件套仍失敗）。
- 任務要求在 ≥3 個互相牽制的約束之間取捨（例：改 dispatcher 同時要相容舊工單、不碰治理檔、又要省 token）。
- 產出將成為之後多個 session 的依據（制度檔、模板、架構決策）。

**不升級，若：**
- 失敗原因是規格不清 → 先修三件套重派同級模型。
- 任務量大但單步簡單（批次改檔、大量搜尋）→ 拆小派多個低階 agent，不是升級。

正例：重寫 CLAUDE.md（未來每 session 都載入）→ 用當下可用的最強模型。
反例：改 50 個檔案的 import 路徑，覺得「量大所以派 opus」→ 錯，這是 haiku/sonnet 批次活。

## 2. 何時算真的完成

全部滿足才算完成，缺一標 `partial`：
1. 每條驗收條件有對應證據（檔案:行號、測試輸出、命令結果碼），不是「我做了」。
2. 通過 fresh-context 驗證（10_DISPATCH_RULES §6），或明確標註 `dispatch_degraded=true`。
3. 交付物路徑寫進回報；Josh 不用問「在哪」。
4. 未解風險與已知限制列出（沒有就寫 none，不准省略此欄）。

正例：「已建 X.md（docs\claude_ops\X.md），驗收 3/3 PASS（fresh read-back，證據：回報第 4-9 行），已知限制：未在 live 環境驗證路徑大小寫。」
反例：「檔案已建立，應該沒問題了。」——沒有證據、沒有驗證、沒有限制欄 → 這是 claimed_by_agent，不是完成。

## 3. 何時該停下來問 Josh

**必問（先停再問）：**
- 命中 RISK_RULES.md 任一條（刪除、金流、憑證、對外寫入、部署、大改核心流程）。
- 兩份正本文件衝突且會影響本次行動方向（例：角色檔說 read-only、AGENTS 說實作者）。
- 任務隱含 Josh 未說出口的偏好且選錯代價 >30 分鐘工作量（例：報告要對內還是對外口吻）。
- 發現任務的前提可能是錯的（例：Josh 要優化一個 current_state 已標記凍結的模組）。

**不問（自己決定並在回報標註假設）：**
- 純技術實作選擇（命名、檔案切分、用哪個標準函式庫）。
- 可低成本回頭的決定（新檔案怎麼組織——反正能改）。
- 答案能從正本文件查到的問題。

正例：Josh 說「把 Antigravity 派工修好」，但 current_state §7 寫 Antigravity 凍結 → 停下來問「這是要解凍嗎？」
反例：不確定報告該用幾個小節，跑去問 Josh → 錯，自己決定、回報時標註即可。

## 4. 什麼訊號代表方向錯了，該換路而非重試

**換路訊號（出現任一就停止重試）：**
- 連續兩次修復都在對抗同一個環境事實（權限、路徑不存在、工具行為和預期不符）→ 環境認知錯了，先派搜尋 agent 重建事實再說。
- 每次修好 A 就壞 B、修好 B 又壞 A → 抽象層選錯，回到規格層重拆。
- 為了讓方案成立，需要的假設越來越多（「只要 X 也成立、Y 也剛好…」）。
- 發現自己在說服自己「這樣應該也算符合驗收」→ 這是在放寬驗收，立即停。

正例：progress_log 2026-07-06 事故——Claude 讀 logs 兩次都 stale，第三次不該再讀，該換路（請 Josh 貼實際輸出／派 agent 用別的命令驗證檔案系統狀態）。
反例：測試失敗一次就整個推翻架構重寫 → 過度反應；一次失敗先讀錯誤訊息。

**重試上限**：同一路徑最多 2 次（與 Workflow v1.2 的 revision 上限一致）；第 3 次前必須換路或升級或問 Josh。

## 5. 文件衝突怎麼裁決

機械流程：
1. 依 AGENTS.md §1 優先序排出兩造層級（Josh 當前指示 > 實際證據 > AGENTS.md > current_state > TASK.md > 角色檔 > progress_log > 聊天記憶）。
2. 高層勝出，照高層執行。
3. **無論誰勝出**，回報 `conflicts_found=<檔案A vs 檔案B, 內容, 採用了誰>`——衝突本身是治理債，靜默選邊 = 讓下一個 session 再踩一次。
4. 若兩造同層級（如兩份角色檔互斥）→ 走 §3 必問。

## 6. 品質底線怎麼驗 ＋ harness 的極限

**可機械驗的（一律要驗）：**
- 檔案：fresh read-back 對驗收條件。
- 程式碼：測試或實跑，含至少一個失敗路徑案例。
- 文件內部一致性：檔內路徑用 `test -f` / `dir` 逐一確認存在。
- 數字與宣稱：每個宣稱回溯到證據行。

**機械驗不了的（誠實條款區）——遇到就選一個處理法並明說，禁止假裝驗過：**
- 對外文案的說服力、報告的口吻是否得體、兩個都正確的架構哪個更好、
  「這份規則會不會太囉嗦」這類品味題。
- 處理法（擇一，寫進回報）：
  (a) 升級模型出第二意見；(b) 多答案評審選優（10_DISPATCH_RULES §6，能提升下限但仍非品味保證）；
  (c) 標 `taste_unverified=true` 交 Josh 定奪；(d) 明說做不到，建議外部人類意見。
- 反例（禁止）：「我覺得文案寫得不錯」寫成驗證通過。感覺不是驗證。
