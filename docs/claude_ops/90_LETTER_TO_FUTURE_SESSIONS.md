## 三件 Josh 沒問、但我認為對這個環境最重要的事

**1. 這個系統最大的風險不是能力不足，是「制度產能」排擠「收入產能」。**
repo 的證據很清楚：治理、路由、監控、記憶架構的文件與腳本佔了絕大多數 commit 量，
而 2026-07-08 稽核報告自己已經下了結論——收入優先、系統優化凍結。
未來的 session 會不斷感受到「再修一下制度」的引力（因為制度工作驗收明確、成就感即時）。
判準寫死：**如果一項工作既不直接產出可賣的交付物、也不是 current_state Priority 清單上的項目，
它預設是不做的**，不管它看起來多合理。本次交付是例外——因為 Josh 明確要求，且它的目的
正是降低之後的制度維護成本，不是增加。

**2. 這個環境的事實層很容易腐爛，而腐爛的事實比沒有事實更危險。**
current_state、README、角色檔已經出現三處互相矛盾（見 00_DIAGNOSIS 漏洞 #2）。
多代理＋多文件的系統，文件同步永遠落後現實。所以行為準則是：
**對任何超過兩週沒更新日期的狀態描述，行動前先用一個命令驗證**（`test -f`、`git log -1 <檔>`、
`type governance_status.json`），驗證成本幾乎為零，而信錯狀態的成本是整個任務方向。

**3. Josh 的核准是系統裡最稀缺的資源，請批次使用。**
治理設計讓大量動作需要 Josh 核准（正確的設計），但這意味著零碎地問會把 Josh 變成瓶頸，
而模型會因為怕煩到人而開始「不問就做」——那是治理崩壞的起點。
正確做法：把需要核准的事**攢成清單一次問**（像 40_MAINTENANCE §3 那樣的核取清單），
每項附一行動機與風險，讓 Josh 能在 30 秒內逐項打勾。零碎問和不問都是錯的。

## 這套制度最可能的退化方式，與預防法

**退化 A：制度檔通膨。** 每個 session 加一點規則，兩個月後 claude_ops 比 AGENTS.md 還肥，
沒人真的照做。預防：40_MAINTENANCE §5 的精簡觸發條件是硬的；且「加規則」的門檻
（先問 Josh）刻意高於「記教訓」（自由 append）——大多數教訓應該停在 50_LESSONS，不該變規則。

**退化 B：驗證儀式化。** read-back 淪為「派個 agent 說 PASS」——驗收條件寫得含糊，
驗證者只能橡皮圖章。預防：T5 模板強制逐條判定與「先找反證」；主對話看到一份全 PASS
但零 issues、零「另案建議」的審查回報，應視為可疑訊號（真的 fresh 審查幾乎總會發現點什麼）。

**退化 C：降級路徑變成常態路徑。** `dispatch_degraded=true` 本該是例外標記，
若連續多個 session 都在降級模式，代表沒人去修 harness 本身。預防：50_LESSONS 若連續
三次出現 degraded 相關記錄，這本身構成一條該向 Josh 提案的制度化事項。

**退化 D：本信被當成正本。** 這封信是判斷與提醒，不是規則。若本信與
AGENTS.md 或 claude_ops 規則檔衝突，本信讓位。
