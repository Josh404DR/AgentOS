# 模型調度守則（Dispatch Rules v1.0）

governance_parent: E:\AgentOS\AGENTS.md
適用對象：擔任主對話的任何 Claude 模型（Sonnet 為基準；規則不依賴更強模型）
從屬關係：本檔不覆寫 AGENTS.md 的角色邊界與 Risky 規則；Risky 一律走 escalation，不派工。

---

## 0. 環境偵測（每個 session 第一次要委派時做一次）

- 若 harness 提供 subagent/Task 工具 → 走 §1–§6 主路徑。
- 若沒有（例如純 Cowork 對話）→ 走 §7 降級路徑。
- 不確定就試派一個 30 秒小任務（「回報 `git rev-parse --short HEAD`」）確認，不要猜。

## 1. 指揮官不下場

主對話（指揮官）的 context 是最貴的資源。以下工作**禁止**在主對話直接執行，一律委派：

| 工作型態 | 判準（滿足即委派） | 委派給 |
|---|---|---|
| 大量讀取 | 預估要開 >3 個檔案，或任一檔 >300 行 | 搜尋型 subagent（模板 T1） |
| 掃 repo | 任何 Glob/Grep 範圍超過單一已知目錄 | 搜尋型 subagent（模板 T1） |
| 查網頁 | 任何需要 >1 次 fetch 的研究 | 研究型 subagent（模板 T4） |
| 批次改檔 | 同一種修改要套用到 >2 個檔案 | 實作型 subagent（模板 T2） |
| 跑測試/長命令 | 預估輸出 >100 行 | 實作型 subagent，只回摘要與結果碼 |

主對話**允許**直接做的：讀單一已知路徑的小檔、寫一個新檔、跑輸出可預期的短命令、
對 subagent 回報做判斷與整合、與 Josh 溝通。

**反例（禁止）**：為了找一個設定值，主對話直接 `grep -r` 整個 repo，300 行輸出進 context。
**正例**：派 T1 subagent「找出 X 設定所在，回傳 檔案:行號 與該行內容，其他不要」。

## 2. 派工三件套（每次委派缺一不可）

1. **目標與動機**：要做什麼＋為什麼（動機讓 subagent 遇到邊角情況時能自行做對的取捨）。
2. **驗收條件**：可機械檢查的完成定義（存在哪個檔、通過哪個命令、回答哪三個問題）。
3. **回報格式**：明確欄位。預設用 §5 回報合約。

沒寫齊三件套就派工＝本守則違規；subagent 回來的東西不可信也不可用。

## 3. 顯式指定 model 與 effort

- 每次委派**顯式**指定 model；harness 若支援思考深度/effort 參數也顯式指定；
  不支援則在 prompt 內寫明深度要求（例如「先列三個候選方案再選一」vs「直接執行，不要展開討論」）。
- 預設分配表：

| 任務 | model | 深度 |
|---|---|---|
| 檔案搜尋、格式檢查、read-back 驗證 | haiku（無則 sonnet） | 低 |
| 一般實作、重構、文件撰寫、研究 | sonnet | 中 |
| 架構決策、含糊需求拆解、高風險審查 | opus 或升級（見 20_JUDGMENT §1） | 高 |

- 升級路徑：sonnet 同一任務失敗 2 次且失敗原因不是「規格不清」→ 升 opus 重派一次。
- 降級路徑：opus 完成後，同型任務下次先試 sonnet；成功 2 次即改預設。
- 規格不清造成的失敗**不准用升級解決**——先修規格（回到三件套），否則 opus 一樣做錯。

## 4. Subagent 回報合約

- 只回：結論、關鍵證據（檔案:行號）、明確的不確定處。
- 長產物（報告、diff、log）落檔到工單 `OUTPUTS\` 或指定路徑，回報只傳路徑。
- 禁止回傳：整段檔案內容、完整命令輸出、推理過程。
- 主對話收到違反合約的回報：摘取結論後**丟棄原文**，並在下次派工 prompt 加強格式要求；
  不要把違規長文留在 context 裡繼續對話。

## 5. 回報最後一行固定附度量（修復 METRICS 斷路，見 00_DIAGNOSIS 漏洞 #3）

```text
metrics: task=<slug> model=<name> wall_time=<秒|unknown> tokens=<實測值|unknown> result=<PASS|FAIL|PARTIAL>
```
主對話負責把這行 append 進 `data\metrics\METRICS_LOG.jsonl`（轉 JSON，欄位同上）。
wall_time 幾乎永遠可實測（記開始/結束時間），不要偷懶填 unknown。
token 依 AGENTS.md §4：拿不到實測值填 unknown，**不得填估算值**。
（00_DIAGNOSIS 提的「標記 estimate 的粗估」是治理變更提案，Josh 核准前不生效。）

## 6. 驗證不自驗

- **檔案類交付**：派 fresh-context subagent 做 read-back——只給它「路徑＋驗收條件」，
  不給實作過程；它回報每條驗收條件 PASS/FAIL 與證據行號。
- **程式碼類交付**：驗收 = 測試或實跑。沒有測試就先寫最小測試；「程式碼看起來對」不是驗收。
- **高風險判斷**（會影響治理、對外、或難回復）：二選一——
  (a) 第二意見：換一個 fresh subagent 用不同角度重答；
  (b) 多答案評審：同題派 2–3 個答案，再派一個 fresh 評審者按驗收條件選優。
- 工單制工作照舊走 Codex Blind Verify；本節補的是工單外日常工作的最低驗證線。
- 實作者與驗證者不得是同一個 context。主對話也不算 fresh——它看過實作過程。

## 7. 降級路徑（harness 無 subagent 時）

按順序退：
1. 用確定性腳本代替委派：`rg` 限定目錄輸出到暫存檔，主對話只讀暫存檔前 N 行摘要。
2. 建 TASK.md 走 Codex queue（Antigravity 依 current_state.md §7 已凍結，不得使用）。
3. 都不行：縮小任務範圍到主對話能安全直做（單檔、短輸出），並在回報中標註
   `dispatch_degraded=true` 讓 Josh 知道這個 session 的驗證強度較低。
禁止的退法：假裝有委派、或直接放棄驗證環節。

## 8. 何時不委派（避免過度制度化）

單檔小修、一句話能答的問題、Josh 在對話中即時追問——直接做。
判準：委派的固定成本約等於「寫三件套＋等待＋整合回報」；預估直做 <2 分鐘且輸出 <50 行就直做。
