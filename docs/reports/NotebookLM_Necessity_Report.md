# NotebookLM 在 AgentOS 中的必要性評估報告

**版本：** 1.0  
**日期：** 2026-06-28  
**狀態：** 決策用草稿  
**核心問題：** NotebookLM 有沒有真的必要存在於 AgentOS？

---

## 一、前提：先定義「必要」

「必要」不等於「有用」。評估標準是：

> 如果移除 NotebookLM，AgentOS 是否有功能性缺口無法被其他已有工具填補？

這份報告從三個角度回答：
1. NotebookLM 實際提供什麼能力
2. 這些能力是否可被替代
3. 保留它的條件與不保留的條件

---

## 二、NotebookLM 實際提供什麼

### 2.1 它真正擅長的事

| 能力 | 說明 |
|---|---|
| 跨文件語意查詢 | 在多份非結構化文件中找到相關段落，並給出引用來源 |
| 自然語言摘要 | 對大量文字生成人類可讀的摘要 |
| 問答追蹤 | 每次回答附帶原始來源，可回溯 |
| Audio Overview | 將知識庫轉成播客式摘要，適合人工快速吸收 |
| Studio 報告 | 半結構化的週期性知識摘要（人工用途） |

### 2.2 它無法做的事（硬性限制）

- **不能直接寫入或修改本機檔案**
- **不能觸發 Agent 執行任務**
- **不能保證輸出是最新狀態**（索引有延遲，內容有同步視窗）
- **不能作為執行證據**（回答是語言模型生成，不是事實查詢）
- **沒有正式公開 API**（`notebooklm-py` 可用，但屬非官方介面，存在失效風險）

### 2.3 它的定位修正（本次討論結論）

原始設計稱其為「決策層」，這是錯誤的。  
正確定位是：**輔助檢索層（Auxiliary Retrieval Layer）**

```
本機 / Git        → 唯一真相來源
NotebookLM        → 輔助語意檢索（不回寫、不觸發執行）
Agent             → 根據本機證據完成決策與任務
```

任何衝突一律採本機版本，並回報 `retrieval_drift`。

## 三、如果沒有 NotebookLM，缺口是什麼

### 3.1 目前 AgentOS 的查詢能力

Agent（Hermes、Codex、Claude）目前處理跨文件問題的方式：
- 直接讀取本機檔案（有路徑才能讀）
- grep / 關鍵字搜索（精確匹配，不具語意理解）
- 從 memory 系統取得摘要（摘要品質取決於寫入時的完整度）

### 3.2 這些方式的已知缺口

| 場景 | 無 NotebookLM 的問題 |
|---|---|
| 「這個決策當初為什麼這樣做？」 | 需要知道哪份文件記錄了這個決策，Agent 才能讀取 |
| 「哪些地方還沒驗證？」 | 需要掃描所有文件，token 成本高，容易遺漏 |
| 「上個月我們做了哪些架構改變？」 | Git log 能提供 commit，但無法直接連結到決策脈絡 |
| 「Hermes 和 Codex 的任務有沒有衝突？」 | 需要同時讀取兩個 Agent 的輸出，手動比對 |
| 人工快速了解現況 | 沒有摘要工具，需要自己讀所有文件 |

**結論：缺口存在，但只對特定場景成立。**

## 四、替代方案分析

如果不用 NotebookLM，有哪些替代方案？

### 方案 A：強化本機 Memory 系統

**做法：** 每次 Agent 執行後，強制寫入結構化摘要到 memory 檔案。Agent 查詢時先讀 memory index。

**優點：**
- 完全本機，不依賴第三方平台
- 沒有 API 失效風險
- 和現有 AgentOS 架構無縫整合

**缺點：**
- 摘要品質取決於寫入 Agent 的表達，容易有遺漏
- 跨文件語意查詢仍然薄弱（keyword-based）
- 人工閱讀體驗差（沒有 Audio Overview、沒有對話式查詢）

**能填補的缺口：** 部分（結構化知識可以，自由問答型查詢不行）

---

### 方案 B：本機向量資料庫（如 ChromaDB、FAISS）

**做法：** 將所有文件 embedding 後存入本機向量資料庫，Agent 透過語意搜索查詢。

**優點：**
- 語意查詢能力接近 NotebookLM
- 完全本機，無同步問題
- 可與 Agent 深度整合，查詢結果直接可程式化使用

**缺點：**
- 需要部署和維護向量資料庫
- 需要 embedding 模型（OpenAI API 或本機模型）
- 沒有人工友好的介面（無對話框、無 Audio Overview）
- 建置成本非零，需要工程時間

**能填補的缺口：** 大部分（Agent 查詢場景幾乎全覆蓋，人工查詢體驗除外）

---

### 方案 C：直接用 Claude 讀取相關文件

**做法：** Agent 遇到跨文件問題時，先透過 grep/index 找到相關檔案，再讀入 context 讓 Claude 回答。

**優點：**
- 零額外工具
- 答案基於最新本機內容，不存在同步延遲

**缺點：**
- Token 成本高（每次都要讀原始文件）
- 依賴 Agent 能正確找到相關文件（grep 有盲點）
- 不適合大規模知識庫（context window 有限）

**能填補的缺口：** 小規模查詢可以，系統性知識查詢不行

---

### 方案比較

| | NotebookLM | 強化 Memory | 向量資料庫 | 直接讀取 |
|---|---|---|---|---|
| 語意查詢品質 | ★★★★★ | ★★☆☆☆ | ★★★★☆ | ★★★☆☆ |
| 人工使用體驗 | ★★★★★ | ★★☆☆☆ | ★★☆☆☆ | ★★★☆☆ |
| Agent 整合深度 | ★★☆☆☆ | ★★★★★ | ★★★★★ | ★★★★★ |
| 平台穩定性 | ★★★☆☆ | ★★★★★ | ★★★★☆ | ★★★★★ |
| 建置成本 | 低 | 中 | 高 | 極低 |
| 維護成本 | 中（同步） | 低 | 中（索引更新） | 極低 |
| 無需網路 | ✗ | ✓ | ✓ | ✓ |

## 五、成本與風險清單

### 保留 NotebookLM 的成本

1. **同步維護成本**：每次本機內容更新，需要重新合併、上傳、等待索引、確認 READY、刪舊版
2. **非官方 API 風險**：`notebooklm-py` 可能在 Google 更新後失效，同步自動化會中斷
3. **索引延遲視窗**：上傳後到可查詢之間有空窗，Agent 可能拿到舊版回答
4. **retrieval_drift 管理**：本機與 NotebookLM 的衝突需要被偵測、回報並處理
5. **依賴外部服務**：Google 可以隨時修改功能、限制配額或停止服務

### 不保留 NotebookLM 的成本

1. **失去對話式知識查詢介面**：人工理解現況需要更多時間
2. **失去 Audio Overview**：沒有快速吸收大量文件的便捷工具
3. **失去跨文件語意搜索**（除非改用向量資料庫）
4. **知識可追溯性降低**：沒有附引用來源的問答功能

## 六、過期機制（校正後版本）

這是架構能正確運作的必要條件。不按統一時間，按文件類型差異化：

| 類型 | 過期邏輯 |
|---|---|
| 環境與外部服務文件 | 7 天強制重新驗證 |
| 操作狀態文件 | 24 小時強制重新驗證 |
| 架構決策文件 | 上游依賴變更時失效（事件觸發，非時間觸發） |
| 歷史事實文件 | 不過期 |

`verified` 狀態不是永久的，是有型別的時效標記。

## 七、品質驗證機制（校正後版本）

不用 AI 評判自然語言，只驗證機器可判定的事實：

```
同步後自動查詢：
  - 最新 Git commit hash 是否出現在 DECISIONS 包？
  - 當前阻礙數量是否與本機 BLOCKERS 檔案一致？
  - 所有 ACTIVE_PROJECTS 的狀態標籤是否存在？

判定規則：
  - 全部吻合 → 同步通過
  - 任一不吻合 → 回報 retrieval_drift，標記本次同步為 stale
  - 不用 NotebookLM 自己回答「架構現況是什麼」來驗證
```

## 八、決策框架：保留或不保留

### 保留 NotebookLM 的條件（需全部成立）

- [ ] **人工查詢是真實需求**：你或團隊確實需要用對話方式查詢 AgentOS 的歷史脈絡
- [ ] **同步自動化可維持**：`notebooklm-py` 穩定，或有人工 fallback 機制
- [ ] **Studio 產物有人真的在用**：週期報告有人閱讀並根據它做決策
- [ ] **不打算建向量資料庫**：沒有工程資源或意願部署本機語意搜索

### 不保留 NotebookLM 的條件（任一成立即考慮移除）

- [ ] Agent 查詢都可以透過本機 memory + grep 覆蓋
- [ ] 沒有人在用 Audio Overview 或 Studio 報告
- [ ] `notebooklm-py` 失效且 Google 沒有提供官方 API
- [ ] 同步維護成本開始干擾主要工作流
- [ ] 已部署本機向量資料庫且效果足夠

## 九、最終結論

### NotebookLM 必要嗎？

**對 Agent 執行而言：不必要。**  
Agent 完成任務所需的所有資訊都在本機，NotebookLM 的回答不能作為執行依據，本機 memory 系統足以支撐 Agent 的跨任務知識查詢。

**對人工理解而言：有條件必要。**  
如果你需要快速用自然語言問「這個系統現在的狀態是什麼」、「某個決策為什麼這樣做」，NotebookLM 提供的對話式查詢和附引用來源的回答是目前最低成本的解法。

**對系統穩健性而言：它的存在不應成為必要條件。**  
NotebookLM 故障、索引延遲、API 失效，都不能讓 AgentOS 停擺。它必須是可選層，而非必要依賴。

### 建議

> 保留 NotebookLM，但降級為「人工輔助工具」，而非系統架構的一部分。
> 
> Agent 的查詢流程不應依賴它。  
> 同步應該是後台低優先級任務，不應阻塞任何 Agent 工作流。  
> 如果某天它失效，AgentOS 的所有核心功能應該不受影響。

這樣它的價值（人工快速理解現況）被保留，它的風險（平台依賴、同步成本、drift 污染）被隔離在邊界之外。

## 附錄：合併包排他分類規則

每個來源檔案只能屬於一個包，判定依據：

| 包名 | 排他定義 |
|---|---|
| `CORE` | 不隨任務改變的系統定義：角色、原則、架構圖 |
| `OPERATIONS` | 目前正在執行的流程與 SOP |
| `MEMORY` | Agent 記憶系統的輸出摘要 |
| `KNOWLEDGE_POOL` | 已完成任務的提煉知識（非當前狀態） |
| `PROJECT_ANALYSIS` | 專案的分析結果，非進行中任務狀態 |
| `RECOMMENDATIONS` | 尚未被採納或執行的建議 |
| `ACTIVE_PROJECTS` | 進行中專案的當前狀態文件 |
| `DECISIONS` | 已做出的決策記錄，含決策時的上下文 |

**邊界衝突解決規則：**  
如果一份文件同時符合兩個包，優先選擇「更窄」的那個。例如一份架構決策同時符合 `CORE` 和 `DECISIONS`，因為它是時間點上的決策，放入 `DECISIONS`。
