# AgentOS 驗證結果標準格式

## 觸發條件

當 Josh 使用「驗證」、「請驗證」、「驗證結果」、「進行驗證環節」或詢問工作是否完成時套用本格式。

如果訊息沒有 dispatch ID、artifact 路徑或檔案路徑，且上下文沒有唯一可辨識的驗證目標，先詢問目標，不得猜測。

## 判定等級

- `成功`：所有核心驗收條件均有實體證據且全部通過。
- `部分成功`：主要流程可用，但至少一項核心或必要條件尚未通過。
- `失敗`：核心流程未完成、結果錯誤或行為不符。
- `阻塞`：缺少權限、憑證、輸入或外部狀態，無法完成驗證。

不得只因有回覆文字、exit code 為零或模型自稱完成就判定成功。

## 固定回答格式

```text
驗證結果：成功 | 部分成功 | 失敗 | 阻塞

摘要：
<一至三句實際結果>

核心細節：
- [達成 | 未達成 | 無法驗證] <核心條件>
  證據：<artifact、log、command output 或狀態欄位>

錯誤的地方：
- <錯誤、嚴重度、影響與證據>
- 若無錯誤，寫「未發現阻斷性錯誤」。

還可以優化的地方：
- <非阻斷性的改善項目>

核心細節達成狀態：
- 已達成：<數量>
- 未達成：<數量>
- 無法驗證：<數量>

證據位置：
- <path 或 log reference>

下一步：
<最小安全動作；完整完成時寫「無必要動作」>
```

## 驗證規則

1. 先定義核心驗收條件，再執行檢查。
2. 每個「達成」必須附實體證據。
3. 區分首次失敗與修正後重跑結果。
4. 舊失敗訊息不得覆蓋同工單較新的成功證據。
5. 修正後成功仍須記錄曾發生的錯誤與修正。
6. `PASS_WITH_CAVEATS` 預設對應「部分成功」；只有非核心 caveat 才可判定成功。
7. 缺少必要 artifact 時不得判定成功。
8. 不得隱藏 source mismatch、認證失敗、模型幻覺或外部上傳失敗。
9. 不得用 NotebookLM、Claude 或 Telegram 回覆取代本地 artifact 驗證。
10. 回答保持精簡，但不得省略固定章節。
